# Checks

**Checks** is active monitoring. You point Flagon at an endpoint, a service, or a scripted
browser flow, and we run it on a schedule from our infrastructure. When it fails or slows
down, we alert you. When it recovers, we tell you that too.

There are two families, and they are priced differently.

## Uptime monitors

Lightweight protocol probes, billed by the number of active monitors:

- **[URL monitor](/docs/checks/uptime)** requests an HTTP endpoint and evaluates its
  status code, response time, and [assertions](/docs/checks/assertions).
- **TCP monitor** opens a connection to a host and port.
- **DNS monitor** resolves a record and checks the answer.
- **SSL monitor** verifies the TLS certificate and warns before it expires.

## Coming soon

**Synthetic checks** (billed per run) are on the way: **API checks** (a request with headers
and a body, run through full assertions) and **Browser checks** (a real browser flow), along
with ICMP, gRPC, heartbeat, multistep, and Playwright suites. Every type is an adapter behind
the same scheduling, alerting, and billing, so they light up without changing how you use
Checks.

## How a run is evaluated

Every run resolves to one of three states:

- **Passing**: the check succeeded within its response-time threshold and every assertion
  held.
- **Degraded**: it succeeded but was slower than the degraded threshold (or, for SSL, the
  certificate is nearing expiry).
- **Failing**: it errored, timed out, or an assertion did not hold.
