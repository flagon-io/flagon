# Runbooks

A **runbook** is a playbook: the ordered steps a responder works through during an
incident. Instead of remembering (or hunting for) the recovery procedure at 3am,
the steps are already on the incident, ready to check off — and they light up as the
incident progresses.

## Writing a runbook

Under **Incidents → Runbooks**, create a runbook and give it steps. Each step is a
**task** (with markdown instructions) or a **link** (to a dashboard, query, or doc).
Steps can also carry **conditions** so they only become active at the right moment —
for example, a "Start the retrospective" step scoped to the **resolved** milestone.

Every org starts with a seeded **Default** runbook so there's always a sensible
playbook; edit or replace it as you like.

## When a runbook attaches

Each runbook has an **attachment** setting:

- **Automatic** — attaches to matching incidents. With no conditions it attaches to
  **every** incident (that's what makes a runbook the default playbook); add
  severity conditions to scope it (for example, only SEV1/SEV2). Attachment is
  **re-checked as the incident evolves**, so a SEV1-only runbook attaches the moment
  an incident escalates to SEV1.
- **Manual only** — never attaches on its own; a responder adds it to an incident by
  hand.

## On an incident

When a runbook attaches, its steps **materialize onto the incident as a checklist**
(a copy — editing the runbook later never changes a live incident). Each step then
evaluates its own conditions against the live incident:

- a step whose conditions hold is **active** — a live to-do responders check off;
- a step still waiting on its conditions is **pending** (it activates the moment
  they're met);
- an integration step whose provider isn't connected is **skipped**, with the reason
  shown, so nothing silently no-ops.

## Over the API

```bash
# A runbook scoped to SEV1/SEV2 incidents (omit attachConditions to attach to all)
curl -X POST .../runbooks \
  -d '{ "key": "db-outage", "name": "DB outage",
        "attachConditions": [ { "type": "severity", "values": ["sev1", "sev2"] } ] }'

# Its steps — a task, a link, and a native "start the retrospective" step gated on resolve
curl -X PUT .../runbooks/db-outage/steps \
  -d '{ "steps": [
        { "title": "Check replica lag", "body": "Run pg_stat_replication", "kind": "task" },
        { "title": "DB dashboard", "kind": "link", "url": "https://grafana/db" },
        { "title": "Start the retrospective", "provider": "core", "action": "start-retro",
          "conditions": [ { "type": "milestone", "values": ["resolved"] } ] } ] }'

# Work the checklist on an incident
curl .../incidents/{number}                 # includes `checklist` with each step's state
curl -X POST .../incidents/{number}/checklist/{itemId}/toggle
```
