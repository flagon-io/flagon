# Projects

A **project** is the unit of the [Catalog](/docs/catalog): the home for one
system you run inside an [organization](/docs/platform/organizations). Every
project has a name and a key, and carries catalog metadata so your workspace is a
described map of what exists rather than a flat list.

## Catalog metadata

Each project can record:

- **Description**: a short summary of what it is.
- **README**: a Markdown README, rendered on the project, for the full story of
  what it is and how it works. Managed by hand today; it will sync from a linked
  repository later.
- **Owning [team](/docs/platform/teams)**: the team responsible for it, so a
  project always has a clear owner.
- **Lifecycle**: planning, in development, alpha, beta, GA, or deprecated.
- **Tier**: a criticality tier from 1 (critical) to 4 (low).
- **Tags**: free-form labels for grouping and search.

Any member of the organization can browse the catalog and open a project. Editing
a project's metadata, and assigning its owning team, is done from the project's
settings by an owner or admin.

## Creating and owning projects

- Owners and admins can always create projects. An organization can also open
  creation up to all members from its settings.
- Assign an **owning team** from a project's settings. The team then shows the
  project under the projects it owns, and its maintainers are the people
  accountable for it.

## Access

Beyond its owner, a project has an **access list**, managed like a GitHub
repository's. Grant a [team](/docs/platform/teams) a role on the project:

- **Read**: view the project and its catalog entry.
- **Triage**: read, plus manage its status and metadata.
- **Write**: contribute to and configure the project.
- **Maintain**: manage the project, short of destructive actions.
- **Admin**: full access, including access and deletion.

The owning team is always an implicit admin. Managing a project's access is done
by an owner or admin from the project's settings.

<Callout tone="note" title="Environments are shared">
Projects organize *what* you're working on; [environments](/docs/platform/environments)
(Production, Preview, Development) are the *stages* each one moves through. The two
compose.
</Callout>

<Callout tone="note" title="Flags are organization-global today">
Feature flags currently live directly under your organization, not inside a
single project. Projects are the catalog's map of your systems; scoping a
product's resources to a project is part of how the catalog grows.
</Callout>
