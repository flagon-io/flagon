A **secret** is any value that grants access if someone else learns it: a
database password, the key to a model provider, an SSO client secret, an access
token. This page lists every secret a Flagon deployment holds, where it lives, and
how it is protected, including the places where protection is access control
rather than encryption. If you self-host Flagon, this is your checklist.

```text
  Environment (set per service)      Databases
 ┌──────────────────────────────┐   ┌───────────────────────────────────┐
 │ API                          │   │ API database                      │
 │   DATABASE_URL               │   │   access tokens     SHA-256 hash  │
 │   FLAGON_APP_DATABASE_URL    │   │   invitation links  SHA-256 hash  │
 │   FLAGON_INTERNAL_TOKEN      │   │   SSO secrets       AES-256-GCM,  │
 │   FLAGON_SECRETS_KEY         │   │                     never read    │
 │   RESEND_API_KEY             │   │                     back to users │
 │   ANTHROPIC_API_KEY          │   │                                   │
 │   FLAGON_AI_API_KEY          │   │                                   │
 ├──────────────────────────────┤   ├───────────────────────────────────┤
 │ app                          │   │ app database (BetterAuth)         │
 │   DATABASE_URL               │   │   passwords, sessions, 2FA        │
 │   BETTER_AUTH_SECRET         │   │   SSO provider cache (plaintext)  │
 │   FLAGON_INTERNAL_TOKEN      │   │                                   │
 │   GOOGLE_CLIENT_SECRET       │   │                                   │
 │   GITHUB_CLIENT_SECRET       │   │                                   │
 │   RESEND_API_KEY             │   │                                   │
 └──────────────────────────────┘   └───────────────────────────────────┘
```

## Secrets in the environment

Both services read their secrets from environment variables. None of them has a
default that is safe outside a laptop, which is why the API's development
defaults apply only in development mode (see
[Configuration](/docs/self-hosting/configuration) for how the mode is chosen) and a
production API refuses to start without the ones marked required below.

### The API

| Variable | What it unlocks | Development default | Production |
| --- | --- | --- | --- |
| `DATABASE_URL` | The migrator role, which owns the schema. Used only at boot. | `postgres://flagon:flagon@localhost:5432/flagon_api` | Required |
| `FLAGON_APP_DATABASE_URL` | The runtime role. Its password is also what the migrator sets when it provisions the role. | `postgres://flagon_app:flagon_app@localhost:5432/flagon_api` | Required |
| `FLAGON_INTERNAL_TOKEN` | Calling the API as any user. Shared with the app. | `dev-internal-token` | Required, and must not be `dev-internal-token` |
| `FLAGON_SECRETS_KEY` | Decrypting the SSO credentials stored in the API database. | A fixed key published in the source | Required |
| `FLAGON_SECRETS_KEYS_RETIRED` | Decrypting SSO credentials sealed under former secrets keys, during a rotation only. | none | Optional |
| `RESEND_API_KEY` | Sending invitation email from the API. | none (emails are written to the server log) | Needed for invitation email |
| `ANTHROPIC_API_KEY` | The Anthropic account the assistant bills to. | none | Optional |
| `FLAGON_AI_API_KEY` (or `OPENAI_API_KEY`) | An OpenAI-compatible model endpoint. | none | Optional |

<Callout type="danger" title="Development defaults are public">
`dev-internal-token` and the development secrets key are readable by anyone in
the source. Anyone who can reach an API running with the development internal
token can act as any user. The API uses these values only in development mode,
and in production it refuses to start without real ones: "FLAGON_INTERNAL_TOKEN is
required in production", "FLAGON_INTERNAL_TOKEN is set to the public development
value", or "FLAGON_SECRETS_KEY is required in production". Generate the internal
token with, for example, `openssl rand -base64 48`, and set the same value on the
app. Generate the secrets key with `openssl rand -base64 32`.
</Callout>

The API loads `.env.local` and then `.env` from its working directory at startup
(a real environment variable always wins over either file). Both patterns are
ignored by git in this repository, so local secrets stay out of commits. The full
list of settings, secret or not, is on
[Configuration](/docs/reference/configuration).

### The app

| Variable | What it unlocks |
| --- | --- |
| `DATABASE_URL` | The app's own database: accounts, sessions, two-factor data. |
| `BETTER_AUTH_SECRET` | BetterAuth's signing secret for sessions and tokens. |
| `FLAGON_INTERNAL_TOKEN` | Calling the API as any user. Must match the API's value. |
| `GOOGLE_CLIENT_SECRET`, `GITHUB_CLIENT_SECRET` | Social sign-in, when configured. |
| `RESEND_API_KEY` | Sending verification and password reset email. |

The compose file in the repository sets development values for these
(`BETTER_AUTH_SECRET: dev-only-secret-change-me-32-characters-min`, and the
default internal token) and sets `FLAGON_ENV: development` on the API. They are
for local use only. In production (`NODE_ENV=production`) the app has no internal
token default: it throws "FLAGON_INTERNAL_TOKEN is required in production" on its
first API call if the variable is unset.

Flagon's own deployment keeps these as platform secrets: Fly.io secrets for the
API and Vercel environment variables for the app. When you self-host, use your
platform's equivalent rather than files baked into an image. See
[Self-hosting in production](/docs/self-hosting/production).

## Secrets in the API database

**Access tokens** are never stored. The API keeps a SHA-256 digest and a short
display prefix; the plaintext is shown once at creation. See
[Tokens and scopes](/docs/security/tokens-and-scopes).

**Invitation links** work the same way: only the SHA-256 digest of the
`flagon_inv_` token is stored, and the link expires after 7 days.

**SSO provider credentials** (an OIDC client secret or a SAML service-provider
signing key) are different, because Flagon has to use them, not just compare
them. They are stored in their own column, `sso_providers.secrets`, separate from
the rest of the provider's configuration, and each value is encrypted.

- **Encrypted at rest.** The API seals each value with AES-256-GCM under
  `FLAGON_SECRETS_KEY` (`api/internal/secrets`). A sealed value looks like
  `enc:v1:<key id>:<ciphertext>`, and each field is bound to its name, so a
  ciphertext copied into another field fails to open. A database dump, backup, or
  replica alone does not reveal the credentials. At every boot the API also seals
  any value still stored in plaintext from before encryption existed, or still
  under a retired key.

- **Write-only to users.** Creating or updating a provider accepts
  `client_secret` or `private_key`. Every user-facing read, whether REST, the
  assistant, or MCP, selects only whether each one is set
  (`client_secret_set`, `private_key_set`), never the value. On update, leaving
  the field out keeps the stored value and an empty string clears it.
- **Readable only by the app.** The one operation that returns them,
  `GET /internal/sso/providers`, accepts only the internal token, so no user or
  access token can reach it. The app uses it to run the sign-in flow.
- **Owners and admins only.** Row-level security restricts the table to the
  organization's owners and admins even for the non-secret fields.

<Callout type="warn" title="The app's SSO cache is plaintext">
The app's BetterAuth SSO plugin caches the full provider configuration, secrets
included, in its own `sso_providers` table in the app database, because the
sign-in flow needs the values in the clear. That copy is not encrypted by Flagon.
Treat backups and read replicas of the app database as holding these credentials.
</Callout>

<Callout type="warn" title="Back up FLAGON_SECRETS_KEY">
A value can be opened only with the key that sealed it. If you replace
`FLAGON_SECRETS_KEY` without keeping the old key as a retired one, values sealed
under it can no longer be opened (the API logs "could not open stored SSO
secrets" at boot) and you must enter each SSO secret again. Back the key up with
the same care as the database.
</Callout>

### Rotating the encryption key

Each sealed value names the key that sealed it, so the API can hold one current
key and any number of retired keys. New values are always sealed under the
current key; retired keys are used only to decrypt.

1. Generate a new key with `openssl rand -base64 32`.
2. Set the new value as `FLAGON_SECRETS_KEY`, and move the old value into
   `FLAGON_SECRETS_KEYS_RETIRED` (a comma-separated list, if more than one
   rotation is in flight). Restart every API machine with the same pair.
3. At boot the API re-seals every stored credential still under a retired key
   with the current key, and logs `encrypted stored credentials at rest under the
   current key` with the row count. This is idempotent, so every machine can do
   it, and reads keep working throughout because the retired key still opens old
   values.
4. Once a boot logs `stored credentials: nothing left to re-seal under the
   current key` with no `could not open stored SSO secrets` warning, remove
   `FLAGON_SECRETS_KEYS_RETIRED` and restart.

Rotation protects against a key that was exposed without the database. If the
database may have leaked too, also rotate the SSO secrets themselves at each
identity provider (see below).

## Secrets in the app database

The app's database belongs to BetterAuth: password hashes, sessions, linked social
and SSO accounts, two-factor secrets and backup codes, and the SSO provider cache
described above. Only the app connects to it; the API never does. How BetterAuth
hashes and protects those values is determined by BetterAuth and its
configuration, not by Flagon's code.

## Secrets and the assistant

The `create_sso_provider` and `update_sso_provider` tools accept a client secret
or signing key as input, so you can configure SSO by asking the assistant.
Anything you type into the assistant, including a secret, is sent to the
configured model provider as part of the conversation, and a proposal's input
travels to your browser for confirmation. If you do not want a credential to pass
through a model provider, enter it on the settings page or through the REST API
instead. See [AI safety](/docs/security/ai-safety).

## What never leaves the API

Errors are the other common leak. The service layer classifies every error into a
caller-safe message. Anything it cannot classify is logged on the server with the
request id and never echoed: REST answers a `5xx` whose detail is a short summary
such as "could not load profile", with the raw cause stripped from the body, and
MCP and the assistant report "something went wrong; please try again". SQL text,
hostnames, connection strings, and model provider responses do not reach callers.
Every response carries an `X-Request-Id` header, so a user can report a failure
and an operator can find it in the log.

## If a secret leaks

| Leaked | Do this |
| --- | --- |
| An access token | Revoke it in the dashboard. It stops working on the next request. |
| The internal token | Generate a new value, set it on the API and the app, and redeploy both. Until then anyone holding it can act as any user. |
| A database URL | Rotate the role's password. For the app role, change `FLAGON_APP_DATABASE_URL`; the API re-applies the password at its next boot. |
| An SSO client secret or key | Rotate it at the identity provider, then update the provider in Flagon. |
| `FLAGON_SECRETS_KEY` | [Rotate the key](#rotating-the-encryption-key) so new ciphertext uses a key the attacker does not have. Treat every stored SSO secret as exposed to whoever also has the database: rotate each at its identity provider and enter the new secrets in Flagon. |
| A model provider key | Revoke it with the provider and set the new one. |
