Most organizations run on **organization roles** and the **base permission**
alone. But sometimes one person or team needs more reach on a **single project**
than the organization gives them. Project access adds **collaborator roles**,
**team grants**, and **ownership** for exactly that, without changing what anyone
can do on other projects.

Everything on this page is managed from a project's **Settings > Access**
(`app.flagon.io/<org>/projects/<project>/settings/access`), which has sections
for collaborators, teams, and owners.

## The roles

A project role is one of five rungs, lowest to highest. The ladder is
cumulative: each role can do everything the ones below it can.

| Role | Grants |
| --- | --- |
| **Read** | See the project, its README, and its collaborators, teams, and owners. |
| **Triage** | Read today. Reserved for work-item powers as deployment and workflow features land. |
| **Write** | Edit the project's name, description, README, and repository URL. |
| **Maintain** | Write, plus renaming the project's slug, and project-level settings (environments and configuration) as they land. |
| **Admin** | Manage the project's collaborators and team grants. |

A person with no effective role on a project cannot see it at all: it is left
out of project lists, and its pages and API operations (reads and writes alike)
return `404 Not Found`. Someone who can see a project but lacks the rung an
operation needs gets `403 Forbidden`. The API checks this in its Go layer and
Postgres row-level security enforces the same rule underneath.

`GET /orgs/{slug}/projects/{project}` (and the `get_project` tool) returns your
own access in a `viewer` object: your effective `role`, whether you are an
`owner`, and the `permissions` that grants (`project:view`, `project:write`,
`project:manage`, `project:admin`, `project:own`). The dashboard uses it to hide
controls you can't use; the server still checks every operation.

**Ownership** sits above the ladder as a separate tier. See
[Project ownership](#project-ownership).

## How access combines

A person can pick up access to a project three ways, and their **effective role**
is the **highest** of them:

- the **organization floor**: what their org role and the base permission grant
  on every project;
- their **explicit collaborator grant** on this project, if any;
- the role of any **team** they belong to that has been granted access to this
  project.

| Org role | Floor project role |
| --- | --- |
| Owner | Admin (plus owner powers) |
| Admin | Admin (plus owner powers) |
| Member | The base permission (default `read`; `none` means no floor) |
| Viewer (legacy) | Read |

Because the effective role is a maximum, a grant can only **raise** someone on a
specific project, never lower them below their organization floor. Granting
`read` to a member whose floor is already `write` changes nothing; granting
`admin` lets that member manage the project's collaborators without making them
an org admin anywhere else. To keep a project private to a group, set the base
permission to `none` and grant access explicitly.

## Collaborators

A **collaborator** is an organization member with an explicit role on one
project. Anyone who can see the project can see its collaborators; people with an
effective `admin` role (or owner powers) can add, change, and remove them.

<Tabs>

<Tab title="Dashboard">

Open the project, go to **Settings > Access**, and add a collaborator by
username or email with a role. Change or remove them from the same list.

</Tab>

<Tab title="API">

```bash
curl -X POST https://api.flagon.io/orgs/acme/projects/billing-api/members \
  -H "Authorization: Bearer $FLAGON_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"login": "dev@example.com", "role": "write"}'
```

</Tab>

<Tab title="Assistant">

Ask: "Give dev@example.com write access to billing-api." The assistant proposes
`add_project_member` and runs it when you confirm.

</Tab>

</Tabs>

- A collaborator must already be a **member of the organization**: a project
  grant elevates an existing member, it never adds outsiders (`409 Conflict`,
  `that user must be an organization member first`).
- You can't change your own grant (`409 Conflict`); another project admin has
  to.
- **Removing** a collaborator drops them back to their organization-level access.
- The person is notified when they are granted access or their role changes.

## Team access

Share a project with a **team** instead of listing people one by one. Grant the
team a role from the ladder and every member of the team inherits it on this
project. A project can be shared with many teams and a team can hold access to
many projects; each grant is independent. Team grants are managed in the same
**Settings > Access** page. See [Teams](/docs/platform/teams).

## Project ownership

**Ownership** is a distinct relation that sits **above** the admin rung. An owner
can do everything an admin can, and in addition:

- **delete and restore** the project;
- **manage the project's owners**, which is also how you transfer a project: add
  the new owner, then remove the old one.

A project can have **multiple owners**, and an owner can be an **individual user
or a team** (making a team an owner makes every member of it an owner). A person
has owner powers when any of these is true:

- they are an org owner or admin (always, on every project);
- they are listed as a direct owner;
- they belong to a team listed as an owner.

Creating a project does **not** make you its owner. A member who creates a
project is instead granted an explicit **admin** collaborator role on it, so
they can manage its access from day one. Because org owners and admins
always hold owner authority, an organization can never be locked out of its own
project even if the explicit owner list is empty. See
[Transfer project ownership](/docs/guides/transfer-project-ownership).

## Operations

| Operation | API | Tool | Scope |
| --- | --- | --- | --- |
| List collaborators | `GET /orgs/{slug}/projects/{project}/members` | `list_project_members` | `read:project` |
| Add a collaborator | `POST /orgs/{slug}/projects/{project}/members` | `add_project_member` | `admin:project` |
| Change a collaborator's role | `PUT /orgs/{slug}/projects/{project}/members/{userId}/role` | `set_project_member_role` | `admin:project` |
| Remove a collaborator | `DELETE /orgs/{slug}/projects/{project}/members/{userId}` | `remove_project_member` | `admin:project` |
| List team grants | `GET /orgs/{slug}/projects/{project}/teams` | `list_project_teams` | `read:project` |
| Grant a team a role | `POST /orgs/{slug}/projects/{project}/teams` | `add_project_team` | `admin:project` |
| Change a team's role | `PUT /orgs/{slug}/projects/{project}/teams/{team}/role` | `set_project_team_role` | `admin:project` |
| Remove a team's access | `DELETE /orgs/{slug}/projects/{project}/teams/{team}` | `remove_project_team` | `admin:project` |
| List owners | `GET /orgs/{slug}/projects/{project}/owners` | `list_project_owners` | `read:project` |
| Add an owner (user or team) | `POST /orgs/{slug}/projects/{project}/owners` | `add_project_owner` | `admin:project` |
| Remove an owner | `DELETE /orgs/{slug}/projects/{project}/owners/{type}/{principalId}` | `remove_project_owner` | `admin:project` |

Collaborator and team management needs an effective project `admin` role; adding
and removing owners needs owner powers, not merely `admin`. Every change is
audited (`project.access_granted`, `project.access_changed`,
`project.access_revoked`, `project.team_access_granted`,
`project.team_access_changed`, `project.team_access_revoked`,
`project.owner_added`, `project.owner_removed`).
