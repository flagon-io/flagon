---
title: Roles & permissions
description: How organization roles, the base permission, project roles, teams, and project ownership combine into what someone can do.
---

Flagon uses a **fixed set of roles**, layered so that broad organization access
and fine-grained per-project access compose predictably. There are four pieces
(organization roles, the base permission, project roles, and team roles) plus a
separate **ownership** relation on projects. Custom roles are not offered: the
vocabulary on this page is the whole model.

On top of roles, every request made with an [access token](/docs/platform/access-tokens)
is also limited by the token's **scopes**. Roles decide what a person can do;
scopes can only narrow that for one credential.

## Organization roles

Every member has exactly one organization role:

| Role | What it can do |
| --- | --- |
| **Owner** | Everything, including deleting and restoring the organization. There must always be at least one owner. |
| **Admin** | Manage members, invitations, teams, organization tokens, the security policy, SSO, and the audit log. |
| **Member** | The default. Project access comes from the **base permission**, raised by explicit grants and team grants. |

Org owners and admins are admins on every project and hold owner authority on
every project, so the organization can never be locked out of its own work.

`viewer` is a legacy read-only organization role. The API still accepts it, and
it is one of the roles an [organization access token](/docs/platform/access-tokens)
can act with, but the dashboard no longer offers it for people: read-only
membership is a member plus a `read` base permission.

## Base permission

The **base permission** is the default project role every member gets on every
project in the organization. Owners and admins set it under
**Settings > Member privileges**.

| Level | Effect on every project |
| --- | --- |
| `none` | No access. Members see only the projects they are granted directly or through a team. |
| `read` | Read. This is the default. |
| `write` | Write. |
| `admin` | Admin. |

The dashboard offers these four (`none` is labeled **No access**). The API and
the `set_org_security` tool also accept the finer `triage` and `maintain` rungs;
anything else returns `422` (`invalid base permission`). A member can be **raised** above
the base on a specific project by an explicit grant, but never dropped below it.
Changes to the base permission are audited as
`organization.security_changed`. See
[Set base permissions](/docs/guides/set-base-permissions).

## Project roles

Projects use a five-rung collaborator ladder. Each rung includes everything
below it.

| Role | Grants |
| --- | --- |
| **Read** | See the project, its README, and its collaborators, teams, and owners. A project you cannot read returns `404 Not Found`, including for write operations, so its existence is not disclosed. |
| **Triage** | Read today. Reserved for work-item powers as deployment and workflow features land. |
| **Write** | Edit the project's name, description, README, and repository URL. |
| **Maintain** | Write, plus renaming the project's slug (it changes the project's URL and breaks outside references) and project-level settings as they land. |
| **Admin** | Manage the project's collaborators and team grants. |

An operation on a project you can read but whose rung you lack returns
`403 Forbidden`. The rules are enforced twice: in the API's Go layer and again
by Postgres row-level security (reading a project row needs read, updating one
needs write), so a missing check in code still can't leak or change a project.

Grants go to an individual collaborator or to a **team**. See
[Project access](/docs/platform/project-access).

## Team roles

A **team** is a named group of members that holds shared project access. Its
internal roles govern the team itself, separate from any project access it
carries:

| Role | What it can do |
| --- | --- |
| **Maintainer** | Manage the team's membership and edit the team. The creator of a team is its first maintainer. |
| **Member** | Belong to the team and inherit its project grants. |

Only org owners and admins create and delete teams. See [Teams](/docs/platform/teams).

## Project ownership

**Ownership** sits **above** the admin rung; it is not a rung on the ladder. An
owner can do everything an admin can, plus **delete and restore** the project and
**manage its owners** (which is how ownership is transferred). A project can have
several owners, and an owner can be an individual user or a team.

Creating a project does not make you its owner. When a member (not an org owner
or admin) creates a project, Flagon grants them an explicit **admin** role on it,
recorded in the audit log as `project.access_granted`, so they can manage what
they created even when the base permission is `read` or `none`. Org owners and
admins are implicit owners of every project; anyone else needs to be added as an
owner.

## How they combine

A person's effective **role** on a project is the highest of:

```text
max( organization floor, explicit project grant, team grants )
```

where the organization floor is `admin` for org owners and admins, the base
permission for members (no floor at all when it is `none`), and `read` for the
legacy `viewer` role. Team grants count only while the person is still on the
team. **Owner powers** apply on top of that role whenever the
person owns the project directly, owns it through a team, or is an org owner or
admin.

For example, in an organization whose base permission is `read`:

| Person | Floor | Grants | Effective |
| --- | --- | --- | --- |
| Org admin | `admin` + owner | none | Admin, with owner powers |
| Member | `read` | none | Read |
| Member | `read` | direct `write` | Write |
| Member on team Platform | `read` | Platform has `admin` | Admin |
| Member on team Release | `read` | Release is a project owner | Read, with owner powers |

## Scopes on top of roles

A token or the assistant never exceeds the person (or service principal) it acts
as. For a token, the effective permission is the intersection of the role above
and the token's scopes: holding `admin:project` does not let a read-only member
delete a project, and an owner using a `read:project` token cannot edit one. The
in-product assistant uses your session, so it is bounded by your role alone. The
[permissions model](/docs/architecture/permissions-model) explains the full
evaluation order.
