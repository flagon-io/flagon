The in-product [assistant](/docs/ai/assistant) and the [MCP server](/docs/ai/mcp)
draw from **one tool registry** (`api/internal/ai`). Every operational tool is the
front door for one real, permission-checked [API](/docs/api/using-the-api)
operation and calls the same service method, so the three front doors cannot
drift. CI enforces the pairing: an API operation that users can call without a
matching tool, or a tool whose scope or read/write nature differs from its
operation, fails the build. This page lists the whole registry: 60 tools.

## How to read the tables

- **API** is the operation the tool runs. Its request and response shapes are in
  the [OpenAPI spec](/docs/api/openapi).
- **Scope** is the [token scope](/docs/platform/access-tokens#scopes) the tool
  requires over MCP, the same scope as its API operation. Parent scopes imply
  their children (`admin:org` covers `write:org` and `read:org`). The in-product
  assistant uses your session, so only your role applies there.
- **Changes data** marks mutating tools. The assistant never runs these on its
  own: it **proposes** them and runs them after you confirm. Over MCP they run as
  soon as they are called, so your client is responsible for confirmation.
- Scopes are a ceiling, never a grant. Every tool also checks your role: for
  example, the SSO and audit tools work only for org owners and admins, whatever
  the token holds.
- Organization tools take the organization's slug as an `org` argument, and
  project and team tools add the project or team slug. The account and
  notification tools act on you and take no organization.
- Any tool call that names an organization first passes that organization's
  [security policy](/docs/platform/two-factor): if it requires two-factor
  authentication or single sign-on and your sign-in does not satisfy it, the call
  fails with 403, on both the assistant and MCP.
- The in-product assistant is confined to the organization its conversation
  belongs to. A call that names any other organization is refused with 403, and
  `restore_organization` (which addresses a deleted organization by id) is
  refused from the assistant entirely; use your personal **Settings >
  Organizations** page for it. MCP has no
  conversation, so a token acts in every organization its user can reach.

## Account and organizations

| Tool | What it does | API | Scope | Changes data |
| --- | --- | --- | --- | --- |
| `whoami` | Your account (id, email) and the organizations you belong to. | `GET /me` | `read:user` | |
| `list_organizations` | List your organizations with your role in each. | `GET /orgs` | `read:org` | |
| `create_organization` | Create an organization you own; the slug is derived from the name if omitted. | `POST /orgs` | `admin:org` | Yes |
| `update_organization` | Rename an organization (owners and admins). The slug does not change. | `PATCH /orgs/{slug}` | `write:org` | Yes |
| `leave_organization` | Leave an organization. The only owner cannot leave. | `POST /orgs/{slug}/leave` | `admin:org` | Yes |
| `delete_organization` | Soft-delete an organization for every member (owners only). Restorable for 30 days. | `DELETE /orgs/{slug}` | `admin:org` | Yes |
| `list_deleted_organizations` | List organizations you owned that were deleted in the last 30 days, with `id` and `purge_at`. | `GET /deleted-orgs` | `read:org` | |
| `restore_organization` | Restore a deleted organization by id, optionally under a new `slug` (owners only, within 30 days). MCP only: the assistant refuses it. | `POST /deleted-orgs/{id}/restore` | `admin:org` | Yes |
| `get_org_security` | Read the security policy: 2FA requirement, SSO requirement, base permission. | `GET /orgs/{slug}/security` | `read:org` | |
| `set_org_security` | Change the security policy (`enforce_two_factor`, `require_sso`, `base_permission`). Only the fields you pass change. | `PUT /orgs/{slug}/security` | `write:org` | Yes |

## Documentation

The documentation tools are the only **public** tools: they are read-only, touch
no tenant data, and need no token. They are the only tools an anonymous MCP
client sees.

| Tool | What it does | API | Scope | Changes data |
| --- | --- | --- | --- | --- |
| `search_docs` | Search the documentation (and, for authenticated callers, internal pages). Returns ranked slugs, titles, and snippets; default 5 results. | none | none | |
| `get_doc` | Read one documentation page in full by slug, such as `platform/projects`. | none | none | |

Pages marked `visibility: internal` (none today; the handbook is public) are served
only to authenticated callers. There is nothing to configure.

| Caller | Pages |
| --- | --- |
| Anonymous MCP client | Public pages only |
| MCP client with an access token | Public and internal pages |
| In-product assistant | Public and internal pages |

The public HTTP routes (`/docs`, `/docs/search`, `/docs/page`) serve the same
corpus, public pages only.

## Not available as tools

A few capabilities deliberately have no tool:

- **Access tokens.** Minting and revoking tokens is dashboard-only, so a
  credential can never create more credentials. See
  [Access tokens](/docs/platform/access-tokens).
- **Your account.** Password, emails, sessions, profile edits, and account
  deletion are managed in **Settings**, so a token or an agent cannot take over
  the account behind it.
- **Internal operations.** Accepting an invitation, SSO provisioning, and the
  sign-in service's SSO configuration reads run only with Flagon's internal
  credential.
